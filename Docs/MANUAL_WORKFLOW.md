# Real experiment without API keys

This guide uses your Claude web subscription to test a first version of a teaching method for a future Claude skill. ChatGPT web can help you find ideas, but keep this first test **Claude versus Claude**: the same displayed model answers the same question once with a plain prompt and once with the proposed teaching instructions. The app stores the pasted answers as real `manual_import` data. Participants, not an AI judge, provide the comprehension results.

**What this test can tell you:** whether this *set of instructions* helped readers understand this one explanation. Repeat it with other topics before treating the method as a general skill. It does not reveal which individual instruction caused a change.

## 1. Start ExplanationLab

If you have not set up the project, follow the [README quick start](../README.md#quick-start) once. Leave `OPENAI_API_KEY` and `ANTHROPIC_API_KEY` blank in `.env`. In two PowerShell terminals, from the project folder, run:

```powershell
# Terminal 1
cd apps/api
.\.venv\Scripts\python.exe -m uvicorn explanationlab.main:app --reload
```

```powershell
# Terminal 2
cd apps/web
npm run dev
```

Open <http://localhost:3000>. The **Demo mode** banner describes answers *generated by the app*. Your manually imported web answers are real and should have an **imported** badge, with **no SYNTHETIC badge**. Do not use **Experiment studio**, **Generate**, **Transform**, or **AI-assisted grading** for this study; without API keys, those model calls use fixtures.

## 2. Create one research question

In **Library → Questions → Add question**, enter:

| Field | Enter |
| --- | --- |
| Question | `How do write-through and write-back caches handle a write, and what are the tradeoffs?` |
| Domain | `software_engineering` |
| Topic | `caching` |
| Conceptual difficulty | `moderate` |
| Factual checklist | Paste the three lines below, one claim per line. |

```text
Write-through writes to the cache and backing store before the write is complete.
Write-back writes to the cache first and sends the changed data to backing storage later.
Write-back can lose unflushed changes if the cache fails; write-through performs more immediate backing-store writes.
```

Click **Create question**. Check these claims yourself before continuing. You can instead use a topic you know well, but then write your own verified checklist and comprehension questions.

## 3. Collect two real Claude answers

In Claude web, use the **same displayed model** for both answers. Start a **new chat for each prompt**. Keep your account settings and tools the same; do not attach files or use web search. Copy the *entire answer text* from each chat, without your prompt or the interface controls. Do not edit either answer. If an answer has a factual error, record it; do not silently repair it.

**Chat A — plain prompt. Paste exactly:**

```text
How do write-through and write-back caches handle a write, and what are the tradeoffs?
```

**Chat B — proposed skill method. Paste exactly:**

```text
How do write-through and write-back caches handle a write, and what are the tradeoffs?

Explain this to someone who understands basic storage but is new to caching. First define cache and backing store in one sentence. Then trace what happens to one write under each policy, in causal order. Give a small concrete example. End with the main tradeoff and one common misunderstanding. Keep the technical claims accurate; do not add a feature that the question did not ask about.
```

Save each prompt and answer in your own notes too. Record the displayed model name and collection date. Your ChatGPT subscription is useful for comparing styles later; it is not needed for these two study arms.

## 4. Import both answers

Go to **Comparison**. Select the research question from step 2. Click **Import a web-chat answer**. Import A, then reopen the form and import B:

| Field | Answer A | Answer B |
| --- | --- | --- |
| Provider | `anthropic` | `anthropic` |
| Model as labelled in the interface | Displayed model name followed by ` — A plain` | Same displayed model name followed by ` — B structured` |
| Pasted answer | Full text from Chat A | Full text from Chat B |
| Capture notes | `Claude web; fresh chat; plain prompt; [date]; [settings]` | `Claude web; fresh chat; structured prompt; [date]; [settings]` |

For example, if Claude displays `Claude Sonnet`, enter `Claude Sonnet — A plain` and `Claude Sonnet — B structured`. The suffix is a **condition label** so you can distinguish arms in this app's results; record the exact displayed model name separately in the notes. Click **Import answer** each time. Confirm both rows show **imported** and neither shows **SYNTHETIC**. Read them side by side and check each factual claim against the checklist.

## 5. Build the human study

Go to **Human evaluation → New study**:

1. **Study name:** `Claude teaching-method pilot — caching`.
2. **Research question:** select the question from step 2.
3. **Conditions:** select only the two imported answers, `A plain` and `B structured`. Exclude every row marked **SYNTHETIC**.
4. Leave **Balance arms** and **Ask prior knowledge** on. Leave the seed at its default. Set **Cap per condition** to `15` if you can recruit 30 people; otherwise leave it blank and treat the result as an exploratory pilot.
5. Replace the three template assessment prompts as follows. Write the correct answer and grading rule *before* recruiting anyone.

| Item | Enter in **Question shown to the participant** | Scoring |
| --- | --- | --- |
| Multiple choice | `A write has been acknowledged. Which policy may still have a changed value only in the cache?` | Options: `Write-through`, `Write-back`, `Both always`. Mark **Write-back** correct. |
| Short answer | `In your own words, trace what happens to one write under write-through and under write-back.` | Keep the **Mechanistic understanding (0–2)** rubric. Give 2 for both paths correct, 1 for one correct, 0 for neither. |
| Scenario application | `A device acknowledges a write, then loses power before pending cache changes reach storage. Which policy is more exposed to losing that change, and why?` | Keep the **Transfer (0–2)** rubric. Give 2 for write-back plus the unflushed-data reason, 1 for the right policy without the reason, 0 otherwise. |

Click **Create study**, then **Open for participants**. On **Setup**, check that neither condition has a **SYNTHETIC** badge. Use **Preview** to inspect the participant flow, but do **not submit a practice response** to the real study; it would enter your results.

## 6. Collect participant responses

On **Setup**, click **Copy** beside the participant link. Each person should participate **once**, without being told which answer they saw. Recruit people who are roughly in the intended learner group; do not use yourself as a participant. Aim for **30 people, about 15 per arm**, for a useful pilot. More people and more topics are needed for a strong general claim.

The copied link contains `localhost` when you run the app locally. That address works **only on your computer**. For an in-person pilot, have participants use the study on that computer one at a time. To send the link to people on other devices, you must first make the web app and API reachable to them; merely sending the `localhost` link will not work. Keep the app and its database running while collecting responses.

## 7. Grade and read the results

After collection, click **Close study**, then **Grading**. Multiple choice is scored automatically. For each short answer and scenario, enter **Human score** using the rules from step 5, add a brief **Grader note**, and save. Grade every free-text answer. The grading screen shows the arm label, so follow the written rules consistently; this grading is not blinded.

Open **Results**. First check that **Ungraded** is `0` for both arms and neither arm has a **SYNTHETIC** badge. Compare the arms' **Comprehension score** and read the uncertainty and small-sample warnings. Clarity and effort ratings are useful context; they are not proof of learning. Click **Generate report** to see the score for each comprehension dimension, including **transfer**, and **Export CSV** to keep the participant-level results.

If B improves comprehension without introducing factual errors, write the tested instructions as a **candidate** Claude skill. Repeat the same procedure on at least two different questions/topics, with fresh participants where possible. If the result disappears or reverses, revise the instructions and test again. This pilot supports a claim about these web-chat answers and participants; it does not prove that a Claude skill will work across all topics or in the API.
